# 设计说明

演出雷达跟踪清单里每位艺人在全国的演出，把几家平台的记录合成一条时间线，阶段一变就推送。本文写它怎么取数、怎么合成、怎么判断阶段、推什么。

## 一轮怎么跑

抓取每 6 小时一轮，北京时间 3:07、9:07、15:07、21:07 前后，每轮随机推迟 0 到 20 分钟。9:07 那轮赶在常见的中午、傍晚开售之前；21:07 那轮接住晚上发的、第二天上午开售的公告。

一轮分七步：

1. 读艺人清单，新出现的艺人写进状态库。
2. 给还没找到平台 ID 的艺人找 ID。找不到的记下时间，7 天后再找；这一轮出错没查成的，下一轮再找。
3. 各平台同时取数，同一个平台里按艺人一位位来，最久没取过的先取。1 小时内取过的艺人跳过。大麦、猫眼、秀动每轮都取；文旅部的库每天凌晨入库一次，只在每天 9 点以后的轮次里取，每位艺人一天取一次。一轮最多取 25 分钟，到点不再取新的艺人，已经取到的照常往下走，没取到的下一轮先取。
4. 把取到的记录和上一轮比，记下新出现的、变了的、这一轮没再出现的。
5. 把记录合成一场场演出，重新判断每场的阶段。
6. 阶段有变化就生成事件，再按事件推送。
7. 检查各平台的健康情况；周一 9 点以后的第一轮发周报。

开售提醒单独跑，每 10 分钟看一次状态库，把 40 分钟内要开售、还没提醒过的场次推出去。它不联网抓取，只发推送。提醒之前先按艺人清单同步一下状态库，直接从清单里删掉的艺人不再提醒；清单是空的不同步，多半是文件被误删或写到一半。

## 艺人清单

艺人清单在运行目录的 `artists.txt`（默认是仓库下的 `.runtime/artists.txt`），第一次用时从 `config/artists.txt` 复制一份底稿。一行一位艺人，第一个名字是主名，后面的别名用顿号或全角逗号隔开。半角逗号算名字的一部分，因为有“Tyler, The Creator”这样的西文名。`#` 后面是注释。

平台 ID 由程序自己找：各平台按主名和别名搜，名字归一以后完全相同的才认。归一指去掉空格和标点、全角转半角、拉丁字母转小写，末尾的“乐队”“乐团”“band”不算。找到的 ID 存进状态库，不写回清单。

- 改了别名，还没找到 ID 的平台下一轮用新别名重找；已经找到的不动。
- 新写的名字已经是另一位艺人的名字或别名时，不新加：同一位艺人跟踪两份，同一场会推两遍。
- 取消关注时，这位艺人还没推出去的消息作废。再关注回来按新关注处理：重新建底、发汇总。
- 手改的清单里，两行的名字或别名撞上，算同一位艺人，只跟踪一行：已经在跟踪的那行优先，都没在跟踪就留前面那行。没跟踪的那行在本机网页上标出来，说清原因。

## 统一记录

每个适配器把平台数据转成统一记录，一条记录是平台上的一个项目，或政府公示里的一条批复。字段定义在 `src/listing.mjs`：

| 字段 | 说明 |
| --- | --- |
| `source` | `damai`、`maoyan`、`showstart`、`gov`（政府公示） |
| `sourceId` | 平台上的项目编号，政府公示是记录 id |
| `artistKey` | 清单里的主名 |
| `kind` | `ticket`（售票项目）或 `approval`（报批） |
| `title`、`city`、`venue` | 项目名称、归一后的城市（不带“市”）、场馆 |
| `dateStart`、`dateEnd` | 演出日期 `YYYY-MM-DD`，北京时间 |
| `matchedBy` | 怎么认定是这位艺人：`id`、`lineup`、`title`、`search` |
| `isMixed` | 音乐节、拼盘这类多位艺人同台的 |
| `status` | `listed`、`presale`、`onsale`、`soldout`、`postponed`、`ended`、`offline`，报批为 null |
| `saleTimes` | 已知的开售时间，毫秒，过去的和将来的都放 |
| `hasSold` | 有证据说明开过票：有退票规则、状态是在售或缺货、某个开售时间已经过了 |
| `roundHint` | 介绍里写的“第 N 次销售”，没有为 null |
| `approval` | 报批才有：批复日期、文号、审批单位、是不是变更 |
| `url` | 给用户点开的页面 |

适配器只管把平台的话翻译成这些字段，不判断阶段。

## 状态库

`.runtime/radar.sqlite`，用 Node 自带的 `node:sqlite`。

| 表 | 存什么 |
| --- | --- |
| `artists`、`artist_ids` | 艺人、别名，各平台 ID 和找 ID 的时间 |
| `artist_sources` | 每位艺人在每个平台上第一次取数成功的时间，用来判断是不是建底 |
| `listings` | 统一记录的最新一份，加首次出现、最近出现、连续缺席轮数 |
| `shows`、`show_listings` | 合成的演出，记录属于哪场演出 |
| `events` | 每次阶段变化，推没推过 |
| `reminders` | 开售提醒发没发过 |
| `source_health` | 每个平台最近成功的时间、连续失败轮数 |
| `runs` | 每轮的开始、结束时间和统计 |
| `kv` | 零碎值：没发出去的文字消息、上次周报时间、文旅部当天的密钥、各适配器按艺人记的备忘 |

适配器写进 `kv` 的备忘先暂存，和这一轮的记录在同一个事务里落盘。一轮中途被杀，备忘和记录一起作废，下一轮照常重取。

## 合成演出

一场演出由艺人、城市、日期定下来。

1. 新记录先找同一位艺人、同一个城市、日期有重叠的演出，前后放宽 1 天。
2. 一边是音乐节或拼盘、另一边是专场时，场馆名对得上才算同一场。各平台判“多人同台”的口径不一样，比如秀动把暖场乐队也算进阵容。报批记录不参与这项比较。
3. 找到几场时，场馆名相同的优先，再看“是否多人同台”一致的，再看开始日期最近的。
4. 没找到就新建一场。
5. 记录归进一场以后不再重新归，免得一轮的结果有出入就把演出拆来拆去。
6. 没有日期的记录先单独成一场，有了日期以后再归一次，对得上别的场就并过去。

城市名去掉末尾的“市”，港澳台去掉开头的“中国”（大麦写“中国澳门”）。政府公示一般用第二级行政区。第二级是“市辖区”这类占位写法时，直辖市和特别行政区用第一级，省直辖的县级市用第三级。

## 阶段

每轮按一场演出名下所有记录重新判断：

| 条件，从上往下看 | 阶段 |
| --- | --- |
| 有售票记录是延期状态 | 延期 |
| 演出日期已过；或者售票记录全部下线、有平台说已结束 | 已结束 |
| 售票记录全部下线，演出日期还没到 | 下架 |
| 没有售票记录，只有报批 | 已报批 |
| 有将来的开售时间，从没开过票 | 待开票 |
| 有将来的开售时间，开过票 | 二开、三开 |
| 有售票记录在售 | 开售 |
| 有售票记录缺货或售罄 | 售罄 |
| 开过票、平台在等下一轮，还没给时间 | 等下一轮 |
| 其他 | 已上架 |

“开过票”记在演出上，一旦为真就不再变回去。售票记录连着两轮没出现才算下架，一轮没取到不算。

演出的日期和场馆用于展示，优先取还在卖的售票记录，其次是全部售票记录，最后才用报批。报批的日期常比真实场次宽，含搭台、彩排日。

### 轮次

首开是第 1 轮。开过票以后，出现一个以前没见过的、将来的开售时间，轮次加 1。第 2 轮叫二开，第 3 轮叫三开，再往后叫“第 N 轮开售”。

- 同一轮分批开售（不同场次不同时间）算同一轮。平台常常只露出下一批的时间，所以上一批刚过、新时间离上一批不到 72 小时，算同一轮的下一批。
- 介绍里写了“第 N 次销售”时，轮次至少是 N。

### 开售时间

各平台给的时间会打架。同一场有几个将来的开售时间时，下一次开售取最早的那个。消息里写明是哪家平台给的；两家给的一样，写两家。

## 推什么

每轮比较演出的前后状态，生成事件。每场演出每轮最多推一条，写到达的最新阶段，顺带说清这一轮新知道的事。

| 事件 | 推不推 |
| --- | --- |
| 已报批 | 推。已经上架的演出补到报批，不单推 |
| 已上架 | 推。同一轮已知开售时间的，直接写成“待开票” |
| 待开票：开售时间公布 | 推 |
| 开售时间改了 | 推 |
| 开售 | 只在没推过开售时间时推，也就是错过了预告 |
| 二开、三开：时间公布 | 推 |
| 售罄或等下一轮以后又在卖，没见到预告 | 推“又有票了” |
| 售罄 | 不推。已报批以后两轮之间直接卖完的，推“已上架（售罄）”；已上架以后两轮之间直接卖完的，推“已开售并售罄”，说明没赶上 |
| 推过的开售时间撤掉了 | 推“开售时间撤了” |
| 延期 | 推 |
| 下架 | 推“下架了，可能取消或改期” |
| 延期或下架以后又在卖了 | 推“恢复售票” |
| 演完了 | 不推 |

同一件事只推一次，按“演出、类型、轮次、开售时间”去重。开售时间已经过了的消息不再推。

### 建底

一位艺人在一个平台上第一次取数成功时，只记录，不按事件推。艺人第一次有平台取数成功时，推一条汇总：

```text
开始关注 薛之谦
大麦、猫眼：找到了；秀动：没有这位艺人
现在有 2 场：
· 无锡 11月13日—22日 待开票 10月27日（周二）17:17 开售
· 厦门 10月31日—11月8日 售罄
```

之后某个平台晚了几轮才第一次取到（第一轮被拦了，或者文旅部隔天才取），它独自找到的演出合成一条补充消息，不逐条推。

### 推送的样子

一条消息同时备好几种写法，各推送通道挑自己用得上的：

- 企业微信用文本卡片，标题 128 字节、描述 512 字节以内。
- Server酱免费版只显示标题，超过 32 字截断。所以每条消息都有一个 32 字以内的短标题，阶段和开售时间写在里面，太长时先截艺人和城市。
- Server酱 和邮件只收合成的一条：一次要推的几条合成一条，开售时间近的排前面。标题写排第一的那条，后面加“等 N 条”。邮件的主题就是这个短标题，正文是纯文字。
- 别的通道照样逐条收：先发文字消息，再发卡片，一轮最多 15 张，多的合成一条清单。
- 一条消息只要有一种通道发出去了就算推过。

### 提醒和健康检查

- 开售前 30 分钟提醒一次。每 10 分钟查一次，所以实际在开售前 30 到 40 分钟之间到。
- 一个平台连着 3 轮被拦或取不到数，推一条：哪个平台、什么原因、别的照常。恢复以后再推一条。
- 还没配推送时，消息不算发出去，留到配好以后再发。
- 周一 9 点以后的第一轮推周报：关注几位艺人、在跟踪几场、这周推了几条、各平台是否正常。

## 请求

- 每个平台一个请求客户端，两次请求至少隔 2.5 秒，超时 20 秒，网络错误重试一次。间隔的下限 2 秒写死在 `http.mjs`；`run`、`check` 放锁之前等满 2 秒，下一个进程也隔开。推送通道不重试，免得重复推。
- 数据源只许请求白名单里的域名。白名单只写在 `http.mjs`，适配器不能自己加。发请求之前查最终的网址，下单、库存、支付、登录、验证码一类的路径，以及大麦白名单以外的接口，一律拦下。
- 同一位艺人在同一个平台上 1 小时内只取一次，记在 `.runtime/fetch-log.json`。名字按归一以后的样子记，去掉“Foo”再关注“foo”还算同一位。去取之前就记，被拦、出错也算取过。`--dry-run` 也守这条。记录的时间在将来（时钟拨过），当作没取过。
- 同一个平台两次 `check` 至少隔 1 分钟。
- HTTP 403、412、429、469，或者认出验证码、滑块，就抛“被拦”，这一轮停掉这个平台，别的照常。
- 认出接口名变了、签名不再被接受，就抛“接口变了”，同样停掉这个平台，并在健康检查里写明原因。
- 同时只跑一轮：`run`、`check` 用 `.runtime/run.lock` 排队，最多等 45 分钟。进程死了留下的锁下次自动清掉。
- 收到停止信号（Ctrl+C、systemd 停服务）时，不再取新的艺人，把已经取到的存下再退出。
- 环境变量 `SHOW_RADAR_LOCAL_ADDRESS` 有值时，请求绑在这个本机地址上。电脑开着全局代理时，可以用它走直连。
- 这些限制是尽力而为：锁、取数记录、进程之间的间隔都记在运行目录里，换一个运行目录就从头算。目的是不误伤各平台，不是防刻意绕开的人。

每位艺人在大麦、猫眼、秀动各 1 到 2 次搜索，状态变了的项目各 1 次详情；文旅部每天每位艺人每个名字搜 1 到 3 页，新记录 1 次详情，两次请求隔 3 秒。关注 20 位艺人，一轮大约 100 到 150 次请求，几个平台同时跑，几分钟跑完。

## 时间

所有时间存成毫秒时间戳。平台给的不带时区的字符串，一律按北京时间解析，显示也一律用北京时间，不看服务器和电脑的时区。

## 命令

| 命令 | 做什么 |
| --- | --- |
| `start` | `daemon` 加上本机网页，并用浏览器打开 |
| `web` | 只开本机网页，不按时抓取 |
| `run` | 跑一轮抓取。`--dry-run` 在状态库的副本上跑，只打印要推的消息；`--artist 名字` 只跑一位；`--source damai` 只跑一个平台；`--force-slow` 不等 9 点，今天还没查过文旅部的艺人也查 |
| `remind` | 跑一次开售提醒，同样认 `--dry-run` |
| `daemon` | 一直跑着，按时抓取、每 10 分钟提醒。抓取和提醒各走各的，抓取再慢也不耽误提醒。两个固定时刻之间最多补一轮：一轮时间到了没取完，半小时后补；一轮一位都没取到、全是 1 小时内取过的，满 1 小时补 |
| `check` | 每个平台发一两个请求，报通、被拦、连不上 |
| `status` | 列出每位艺人在跟踪的演出和阶段 |
| `follow`、`unfollow` | 改艺人清单 |
| `setup-push`、`test-push` | 配推送、发测试消息 |

推送密钥放在 `.runtime/secrets.env`：

| 通道 | 键 |
| --- | --- |
| Server酱 | `SERVERCHAN_SENDKEY` |
| 邮件 | `SMTP_USER`（完整邮箱地址）、`SMTP_PASS`（授权码）；收件人不是自己再写 `MAIL_TO`；QQ、Foxmail、163、126 以外的邮箱再写 `SMTP_HOST`，这几种邮箱写了也不用 |
| WxPusher | `WXPUSHER_SPT` |
| Bark | `BARK_KEY`，自建服务器再写 `BARK_SERVER` |
| 企业微信 | `WECOM_CORP_ID`、`WECOM_AGENT_ID`、`WECOM_SECRET`、`WECOM_TO_USER`。接收人必填，不默认推给 `@all` |

同名的环境变量优先，邮件的几项除外。`SMTP_HOST` 这类名字别的程序也常用，碰巧设了一个，授权码就会被送到别人的服务器上。环境变量盖过了刚存的值、去掉通道时环境变量里还有，网页和 `setup-push` 都会说出来。

## 本机网页

给自己部署的人在浏览器里加艺人、配推送、看演出，不用敲命令。不做放在别人服务器上、大家注册进来的平台。那样要替别人保管邮箱授权码，所有人的请求也都从一个 IP 出去。

网页和命令行调的是同一份操作（`app.mjs`）。填推送密钥的规矩写在 `app.mjs` 的 `PUSH_CHANNELS` 里，命令行照着一项项问，网页照着画表单，检查走同一个函数。

网页上只留标签、按钮、状态和出错时下一步做什么。怎么配、为什么写在 README，网页上用“使用说明”“怎么配”两种链接指过去。

界面照苹果的界面规矩做：系统字体，分组的圆角卡片，大标题滚上去以后顶栏才变成半透明，按下就有反馈。动效只动位移、缩放和透明度。深色模式、减少动态、降低透明度、增强对比度都跟着系统。

网页能改推送密钥、能触发请求，只给这台电脑上的这个人用：

- 只监听 `127.0.0.1`。
- 接口要带钥匙才能用。页面、脚本、样式里没有要保密的东西，不用钥匙。
- 钥匙每次启动随机生成，服务端只放在内存里、不落盘，进程一退就作废。链接会出现在终端和日志里，漏了也只在这次运行里有用。
- 钥匙放在链接的 `#key=` 后面，浏览器不会把它发给服务器。页面把它存进这个端口的 `localStorage`，从地址栏去掉，之后每个请求放在 `X-Show-Radar` 头里带上。
- 不用 Cookie。浏览器的 Cookie 不分端口，会被带给本机别的服务；`localStorage` 和请求头只属于这个页面。
- 别的网站的页面要带 `X-Show-Radar` 头，浏览器会先发预检，这里不答，请求就发不出来。改东西的请求带了 `Origin` 的，要是本页面（浏览器跨站发的请求一定带）。
- 只认 `Host` 是 `127.0.0.1`、`localhost` 的请求，防 DNS 重绑定。
- 接口从不返回密钥的值，只说配没配好。Bark 自建服务器的地址只给主机名。
- 填的值里有换行或控制字符，一律不存，免得在 `secrets.env` 里多写出一行。
- 内容安全策略只放行本站，页面不加载任何外部资源。平台给的文字一律当文字显示，不当 HTML。

同一个进程里，常驻的那一轮、网页上点的“现在抓一轮”“检查各平台”不能同时做。到点时网页上点的那一轮正在跑，就算这一轮，不再接着跑一遍。进程之间照旧用 `run.lock` 排队。网页上的“检查各平台”遇到别的进程在跑一轮，最多等 5 秒，等不到就说一声，不让人干等。

## 数据源

### 大麦

走手机网页的接口，只用搜索和项目详情两个，不碰票档库存。请求要带网页前端算的签名，令牌来自服务器下发的匿名 Cookie，不登录。

- 艺人：搜索结果里 `type=2` 的是艺人账号，`damaiId` 是艺人 ID。
- 项目：`artisteNames` 里有这位艺人，或者项目出现在他账号的演出列表里，才算他的演出。周边（分类“其他”）去掉。
- 售票状态 `itemSaleStatus`：0 热卖，1 缺货，2 预约（等首开或等下一轮），7 延期。
- 开售时间：列表上的预约时间，详情里各场次的开售时间，介绍里写的“第二次销售时间”。
- 开过票的证据：详情里有退票规则，规则的起点一般就是首开时间。场次开售时间还在将来的，不算开过票：开售改过期的项目，退票规则会留着改期前的旧时间。
- 什么时候取详情：新项目，列表上的状态或开售时间变了，预约中却还不知道下一次开售时间，或者上一轮详情没取到。

### 猫眼

走大众点评网关，匿名、不签名。按关键词搜全国，开售时间和售票状态以详情为准。

- 售票状态 `ticketStatus`：1 即将开售，2 预售，3 在售，4 售罄，5 已结束，11 即将预售，12 延期。
- 分类只留演唱会、音乐节、Livehouse。
- 阵容里有这位艺人，或者演出名里有艺人名又不是致敬场，算命中。
- 艺人 ID 只用来核对音乐节阵容，取不到时照样按名字搜。

致敬场各平台共用 `src/text.mjs` 的规则：标题带“致敬”“tribute”“模仿秀”“翻唱”，或者艺人名后面紧跟“金曲”“经典歌曲”这类字，都去掉。

### 秀动

Livehouse、独立乐队和音乐节的主力。网页接口匿名可用，每个请求带网页前端算的签名。签名的写法和 RSSHub 的秀动路由一样。

- 先按名字找音乐人 ID，再按 ID 取全国还没开演的场次。名字常有繁简两种录法，两种都试。
- 详情里每个票档有开售时间和状态。价格为 0 或写着“待定”的是占位票档，不算开售时间。
- 没有售罄字段：真实票档都停售了，记成售罄。
- 什么时候取详情：新场次、列表上的标题时间价格变了、上一轮在等开售；在卖的场次每天重取一次，因为二开常常是加一档更贵的票，列表上看不出来。

### 文旅部

查文化和旅游部政务服务平台上的“全国涉外营业性演出活动”，管时间线上“已报批”这一格。

- 只有涉外演出，也就是有港澳台或外国演员参演的。内地艺人的演出多由区县审批，不公示。
- 库里没有演员字段，只能拿艺人的主名和别名去搜演出名称。站点按原文模糊搜，繁体和简体不互通，两种写法都要写进别名。
- 只搜今天以后开始的演出。列表按开始日期倒序，一个名字超过 3 页时取第 1 页和最后 2 页，开演最近的不会漏。
- 新出现的记录取一次详情，见过的沿用上一轮，批复内容不会变。
- 只存演出名、日期、城市、场馆、文号、批复日期和审批单位。报批单位、报批地和个人信息不存。
- 演出名里有“变更”“增加演员”“延期”“取消”的，记作变更批复。
- 请求和响应都用站点自己的 SM4 写法加密，密钥每天由站点下发，不用 Cookie。站点的循环左移用了有符号右移，算出来和标准 SM4 不一样，所以照站点的脚本实现，不用 `node:crypto`。
- 库每天凌晨 1 点半前后入库，零点前后接口会挂住。所以只在每天 9 点以后的轮次里取，每位艺人一天一次。

## 测试

- 适配器把“发请求”和“解析”分开。解析是纯函数，用 `fixtures/` 里存下的真实响应测。大麦、猫眼、秀动的样本删掉了第三方用户的内容和联系方式；文旅部的样本里没有个人信息，原样保留。
- 文旅部的 SM4 用 `fixtures/gov-national/` 里的密文和解密结果对照测。
- 合成、阶段、轮次、事件用手写的记录序列测，覆盖首开、分批开售、改时间、二开、售罄又有票、延期、下架、建底。
- 时间解析在不同的 `TZ` 下测，结果一样。
- `tests/guards.test.mjs` 检查请求间隔下限、艺人上限、锁、时刻表、请求前的网址检查，并扫一遍代码里的网址和接口路径。
- 测试不联网，运行 `npm test`。
